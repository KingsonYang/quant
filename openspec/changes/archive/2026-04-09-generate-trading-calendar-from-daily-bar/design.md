## Context

当前仓库已经具备以下基础：

- `sql/schema_v1.sql` 中已定义 `trading_calendar` 表
- `daily_bar` 已作为标准化日线行情表落地，并且其中的 `trade_date` 均可视为真实交易日
- CLI 已采用 Typer，并以 `quant <command>` 形式暴露数据库初始化和百度行情导入能力

现状问题在于：交易日历虽然有表结构，但没有生成逻辑，也没有命令入口，因此回测引擎未来若需要“跳过非交易日”“找到前一交易日/后一交易日”，仍然缺少可靠数据来源。

这个需求的边界比较明确：不从外部交易所或日历接口抓取数据，而是完全基于现有 `daily_bar` 推导交易日。这样可以先落地一个与当前数据底座一致的最小版本。

## Goals / Non-Goals

**Goals:**

- 提供一个全量命令，从 `daily_bar` 中读取所有唯一 `trade_date` 并生成 `trading_calendar`
- 提供一个增量命令，只补充 `trading_calendar` 中尚不存在的交易日
- 在写入时为每个交易日维护 `prev_trade_date` 与 `next_trade_date`
- 保持 `market='ab'` 的单市场实现，和现有 A 股数据范围一致
- 输出清晰的执行摘要，便于验证写入数量和模式

**Non-Goals:**

- 不引入外部交易日历数据源
- 不补充非交易日记录，也不尝试生成完整自然日历
- 不处理多市场、多交易所差异化日历
- 不在本次变更中实现回测引擎读取交易日历的逻辑

## Decisions

### 1. 交易日来源直接使用 `daily_bar.trade_date`

采用 `daily_bar` 中的唯一日期集合，按升序生成交易日历，而不是额外维护独立数据源。

原因：

- 当前仓库最可信、最一致的交易日来源就是已入库的日线行情
- 实现成本低，能快速把“表结构”变成“可用数据”
- 与用户需求一致，避免额外抓取链路和数据校验复杂度

备选方案：

- 外部交易所日历接口：更完整，但超出当前项目阶段
- 手工维护 CSV/静态文件：维护成本高，且容易与 `daily_bar` 脱节

### 2. 全量模式采用重建式写入

全量命令将查询全部唯一交易日，并按排序结果重建 `trading_calendar` 中 `market='ab'` 的记录。

原因：

- `prev_trade_date` / `next_trade_date` 是链式关系，全量模式重建最简单、最不易出现残留脏数据
- 使用者对“全量”命令的预期通常就是重新生成一份完整结果

备选方案：

- 对现有记录逐条 upsert：可行，但更复杂，且不如重建清晰

### 3. 增量模式采用补充缺失日期后重算相邻关系

增量命令将从 `daily_bar` 中找出 `trading_calendar` 尚不存在的日期，补充后再统一更新受影响记录的前后交易日关系。

原因：

- 仅插入新日期但不更新相邻关系，会导致旧尾部记录的 `next_trade_date` 或新记录的 `prev_trade_date` 不正确
- 交易日数量远小于日线总量，在当前阶段允许用简单而稳定的重算逻辑换取正确性

备选方案：

- 只更新新增记录附近两端：更高效，但实现更容易遗漏边界情况

### 4. 命令入口保持与现有 CLI 风格一致

新增两个 Typer 命令，建议命名为：

- `quant build-trading-calendar`
- `quant build-trading-calendar-incremental`

原因：

- 与现有 `init-db`、`ingest-baidu-all` 风格一致，语义直观
- 区分全量与增量模式，便于自动化任务调用

备选方案：

- 用一个命令加 `--incremental` 参数：也可行，但不如两个明确入口清晰

## Risks / Trade-offs

- [风险] `daily_bar` 只覆盖已导入股票的交易日，若历史数据不完整，生成的交易日历也会不完整
  → 缓解：在命令说明和摘要中明确该日历来源于当前库内 `daily_bar` 覆盖范围

- [风险] 全量重建会覆盖 `market='ab'` 既有日历记录
  → 缓解：将全量模式明确定义为重建行为，并限定作用范围为 `ab` 市场

- [风险] 增量模式若只追加不重算前后链，会造成相邻日期关系错误
  → 缓解：增量补充后统一重算 `prev_trade_date` / `next_trade_date`

- [权衡] 当前不记录非交易日，自然日到交易日的映射能力有限
  → 缓解：先满足回测引擎按交易日推进的最小需求，完整自然日历后续再扩展
