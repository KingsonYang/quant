## Context

当前仓库已明确项目方向为面向 A 股市场的日线回测系统，技术栈采用 Python、pandas、DuckDB/Parquet、Typer 和 pytest。现阶段仓库中仅有数据来源说明与样例文档，尚未建立统一的数据模型、标准字段口径、表关系和回测结果存储规范。

已有数据来源以百度 A 股日 K 数据为基础，主要包括两类信息：

- 日线行情：以 JSONP 返回，核心字段位于 `newMarketData.marketData`，可解析出时间、开高低收、成交量、成交额、涨跌额、涨跌幅、换手率、昨收以及均线相关字段。
- 事件数据：位于 `reportData`，可映射为特定交易日期上的财报发布类事件。

该数据形态决定第一版应优先支持日线级、收盘后计算信号、次日成交的回测模型。为了让后续的数据抓取、标准化处理、查询分析和回测执行使用统一的数据契约，需要先设计一版完整但不过度复杂的数据表结构。

## Goals / Non-Goals

**Goals:**

- 为第一版系统定义统一的数据层模型，覆盖证券主数据、交易日历、原始响应、标准化日线行情、事件数据和回测结果数据。
- 明确“原始层、标准层、结果层”的分层职责，避免采集逻辑与回测逻辑直接耦合。
- 为 DuckDB/Parquet 落地提供稳定的主键、唯一键、分区建议和字段口径约定。
- 支持单股、股票池、多策略、多次回测任务的后续扩展。
- 保证第一版表结构天然适配“收盘信号、次日成交、T+1、日线级撮合”的回测模式。

**Non-Goals:**

- 本次不实现具体的数据采集程序、解析程序和回测引擎代码。
- 本次不覆盖分钟级、Tick 级或盘口级数据模型。
- 本次不设计实盘交易、账户对接或券商接口表结构。
- 本次不解决完整复权、停牌、ST、板块涨跌幅规则的全量主数据来源问题，只为后续扩展预留字段与关系。

## Decisions

### 1. 采用三层数据域：原始层、标准层、结果层

系统的数据表按职责分为三层：

- 原始层：保存抓取到的原始请求与响应，便于重放、审计和排查解析问题。
- 标准层：保存标准化后的证券主数据、交易日历、日线行情、事件数据，是策略和回测统一读取的数据来源。
- 结果层：保存策略定义、回测任务、订单、成交、持仓快照、每日权益等运行产物。

选择该方案而不是只保留标准表，有两个原因：

- 百度数据源当前返回 JSONP，后续解析逻辑可能调整，保留原始层可以避免重新抓数。
- 回测结果具有实验属性，与市场数据生命周期不同，单独分层更利于清理和复现。

备选方案是“仅保留标准层 + 本地文件缓存”。该方案更轻，但不利于问题定位和结果追溯，因此不作为第一版主方案。

### 2. 标准层以“证券 + 交易日”为核心联合主键

第一版核心标准表中的日线数据采用 `(symbol, trade_date)` 作为联合主键，证券主数据采用稳定的内部 `security_id` 与外部 `symbol` 双标识。

这样设计而不是所有表都只使用字符串代码，是为了兼顾：

- 对接外部数据源时保留原始代码口径
- 内部关联时使用稳定主键，降低代码改名、退市重映射等影响
- 后续支持同一证券多市场标识、多数据源映射

### 3. 事件数据单独建表，不内嵌到日线行情表

财报类事件源于 `reportData`，天然是“一天多事件”结构，因此单独设计事件表，并通过 `(security_id, event_date)` 与行情表关联，而不是把事件字段平铺进日线表。

这样做的原因：

- 同一天可能出现多条事件记录
- 事件类型未来不只财报，可能扩展到停牌、公告、分红、股东减持等
- 单独建表更适合事件驱动策略与多标签分析

备选方案是将财报字段直接挂到日线表上。该方案查询方便，但扩展性差，也不适合多事件场景。

### 4. 回测结果采用“任务 - 订单 - 成交 - 持仓 - 权益”链路建模

第一版回测结果表按以下关系组织：

- 策略定义表：描述策略元数据和参数模板
- 回测任务表：描述一次具体运行
- 订单表：描述策略在某交易日生成的委托意图
- 成交表：描述实际撮合结果
- 持仓快照表：描述某日收盘后的持仓状态
- 每日权益表：描述某日净值、现金、持仓市值、收益等

这是典型的研究回测链路，优于仅保存净值曲线的简化方案，因为：

- 可以追溯每笔交易产生的原因与影响
- 更容易验证 T+1、涨跌停未成交、滑点和费用处理
- 为后续做交易分析、归因分析、调仓分析打基础

### 5. 第一版优先为 DuckDB 表设计逻辑模型，同时允许落地为 Parquet 数据集

第一版设计文档中的“表”是逻辑表结构，不限定必须长期以数据库实体存在。推荐实现时采用：

- 原始层与标准层优先落地为 Parquet 数据集
- 查询、联表、回测预处理时由 DuckDB 读取 Parquet
- 小规模元数据与回测任务结果可以直接落在 DuckDB 文件中

这样设计而不是全部使用关系数据库，是因为该项目初期更偏本地研究型工作负载，列式存储与分析查询效率更匹配。

## Risks / Trade-offs

- [风险] 第一版表结构不足以完整表达复权、停牌、ST 和板块差异规则 → 通过预留扩展字段和后续补充辅助表缓解，不在首版过度设计。
- [风险] 同时维护 `security_id` 和 `symbol` 两套标识会增加实现复杂度 → 通过明确“内部关联优先 `security_id`、对外展示使用 `symbol`”的约定降低混乱。
- [风险] 原始层、标准层、结果层分层后表数量较多，初期理解成本会上升 → 通过在规范中标注“首版必须表”和“后续扩展表”控制实现优先级。
- [风险] DuckDB/Parquet 适合研究型分析，但在线并发写入能力有限 → 第一版目标是单机研究与回测，不追求高并发写入，可接受该权衡。
- [风险] 数据源本身为非正式结构化接口，字段可能变动 → 保留原始响应表并为解析产物建立版本字段，便于回溯和兼容处理。
