## Context

当前仓库已经具备以下前提：

- `security_master` 可提供证券代码、市场、板块、上市状态等基础过滤字段
- `daily_bar` 可提供价格、涨跌幅、成交额、换手率、均线和均量等技术面字段
- `event_record` 可提供基础事件过滤能力，目前以 `financial_report` 为主
- `trading_calendar` 可提供交易日对齐和目标交易日校验能力

现阶段最合适的选股模块不是自然语言系统，而是一个“固定规则、可拼接、参数驱动”的执行层。原因是当前数据能力已经能支持一批明确的技术面和基础事件条件，但还不具备支撑口语化表达所需的语义解释、能力发现和错误恢复机制。

## Goals / Non-Goals

**Goals:**

- 定义第一版选股规则的结构化参数格式
- 支持在指定交易日基于已有标准层数据执行选股
- 支持多个固定规则条件按可预期的方式组合
- 支持窗口型派生规则和白名单排序字段
- 提供一个 CLI 入口，接收参数并输出选股结果
- 约束第一版规则范围，仅覆盖当前数据能稳定支持的条件

**Non-Goals:**

- 不实现自然语言到选股规则的转义
- 不引入当前数据模型之外的新因子、新行情源或新财务数据
- 不在本次变更中实现回测引擎与选股模块的深度联动
- 不支持任意表达式执行或用户自定义 SQL

## Decisions

### 1. 规则表达采用固定字段 + 固定操作符的结构化参数

第一版选股条件采用固定 schema，例如“字段 + 操作符 + 值”的规则对象列表，而不是自由表达式字符串。

原因：

- 更容易做参数校验和错误提示
- 可以严格限制在当前数据支持范围内
- 便于后续转换成 SQL 查询或 DuckDB 条件

备选方案：

- 直接传 SQL：灵活但不安全，也不利于产品化
- 自定义表达式语言：能力更强，但第一版成本过高

### 2. 条件组合仅支持固定逻辑拼接

第一版组合逻辑以 `AND` 为主，可预留 `OR` 扩展，但不做复杂嵌套逻辑树。

原因：

- 大多数第一版选股场景都能用交集筛选完成
- 可以大幅降低参数结构和实现复杂度
- 结果更稳定、可解释性更强

备选方案：

- 支持任意嵌套布尔树：更通用，但超出当前阶段

### 3. 规则范围只覆盖当前已落地数据

第一版允许的规则类型建议包括：

- 证券基础过滤：`exchange`、`board`、`list_status`、上市天数
- 当日日线字段：`close_price`、`change_pct`、`turnover_ratio`、`amount`
- 均线与均量关系：`close_price > ma20_price`、`volume > ma5_volume`
- 基础事件过滤：最近 N 天是否存在 `financial_report`

原因：

- 这些字段已在当前 schema 中稳定存在
- 不需要依赖未来扩展表
- 适合快速形成一个最小可用的选股器

### 4. 执行层优先生成 DuckDB 查询

选股执行时优先将规则翻译成面向 DuckDB 的查询，并输出结果表或终端摘要。

原因：

- 当前数据已经落在 DuckDB
- 查询式执行更贴合选股任务
- 后续如果做回测联动，也更容易把选股结果作为股票池输入

备选方案：

- 先把数据拉到 Python 再逐条筛选：更直观，但在数据规模扩大后效率和维护性更差

### 5. 窗口型规则基于交易日序列计算

窗口型规则通过 DuckDB 窗口函数在单证券时间序列上计算，例如“前 5 个交易日平均成交量”“前 5 个交易日成交量总和”和“当日成交量 / 前 5 日均量”。

原因：

- 可以直接复用 `daily_bar` 与 `trading_calendar` 的交易日定义
- 明确“前 N 日”是交易日窗口而非自然日窗口
- 能用统一查询层同时支持筛选条件和排序字段

### 6. 排序能力采用固定白名单字段

排序不开放任意表达式，只支持固定白名单字段，例如 `close_price`、`volume`、`prev_5d_avg_volume` 和 `volume_plus_prev_5d_sum`。

原因：

- 更容易保证结果稳定性和可解释性
- 与固定规则模式保持一致
- 可以避免任意排序表达式带来的实现复杂度

## Risks / Trade-offs

- [风险] 当前可支持的规则范围有限，用户容易期待基本面或行业因子
  → 缓解：明确规则白名单，并在 CLI 帮助和文档中写清第一版支持范围

- [风险] 若参数结构设计过于刚性，后续扩展新规则会变得困难
  → 缓解：从第一版开始就采用统一规则对象列表，而不是为每个条件单独设计命令参数

- [风险] 事件规则若直接基于文本内容，会出现口径不稳定
  → 缓解：第一版仅支持 `event_type` 和最近 N 天存在性这类稳定过滤，不做事件文本语义解析

- [权衡] 不做自然语言入口会牺牲一部分易用性
  → 缓解：先把结构化执行层打稳，后续若需要口语化入口，再做“自然语言转结构化规则”的上层适配
