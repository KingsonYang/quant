## Context

当前仓库已经具备两类回测能力：

- 普通回测：由 `quant backtest-selection` 驱动，输出汇总统计和逐笔明细。
- 策略回测：由 `quant backtest-strategy` 驱动，输出账户汇总和交易记录。

但这两类能力都只通过 CLI 暴露，结果以控制台文本为主，不适合在大量记录下进行浏览、筛选和反复调参。项目当前技术栈以 Python 为中心，没有现成的前端工程、Node 构建链路或 Web 服务层，因此本次设计需要在尽量复用现有回测核心逻辑的前提下，引入一个最小可维护的 Web 展示层。

## Goals / Non-Goals

**Goals:**
- 为普通回测和策略回测各提供一个可直接访问的 Web 页面。
- 提供统一的页面导航、参数表单、运行状态、错误提示和空结果展示。
- 复用现有 `backtest.py`、`strategy_backtest.py` 和规则解析逻辑，不重写回测计算。
- 将 CLI 当前的领域结果对象转换为结构化视图模型，支持页面渲染和后续接口复用。
- 在不引入独立前端仓库的前提下，形成一套可测试、可扩展的 Web 入口。

**Non-Goals:**
- 不替换现有 CLI 命令，也不要求 CLI 输出格式与页面完全一致。
- 不在本次变更中实现用户登录、任务队列、异步作业管理或历史任务持久化。
- 不引入复杂单页应用框架、前后端分仓或 Node 构建流程。
- 不扩展新的回测规则、资金模型或数据库表结构。

## Decisions

### 1. 采用轻量 Python Web 服务，而不是独立前端工程

新增一个轻量 Web 应用层，直接运行在当前 Python 项目中，负责：

- 提供页面路由，如 `/backtests/selection` 和 `/backtests/strategy`
- 接收表单参数并执行校验
- 调用现有回测领域服务
- 将回测结果转换为 HTML 页面所需的展示模型
- 同时暴露 JSON 接口，便于后续演进

选择原因：

- 当前仓库没有前端基础设施，直接上独立前端会引入额外包管理、构建、部署和跨语言维护成本。
- 现有回测逻辑都在 Python 中，Web 层贴近领域层能减少重复封装。
- 服务端渲染足以覆盖本次“参数输入 + 结果浏览”的核心目标。

备选方案：

- React/Vue 独立前端 + Python API。未采用，因为对当前阶段属于过度设计。
- 继续只输出 JSON 文件供人工查看。未采用，因为仍无法解决交互式筛选与集中查看问题。

### 2. 页面采用服务端渲染，结果表格与统计卡片由后端直接生成

首版页面以服务端渲染为主，必要时用少量原生 JavaScript 增强交互，例如表格折叠、结果区定位或简单筛选。页面结构统一为：

- 顶部导航：普通回测 / 策略回测
- 左侧或顶部参数区
- 提交后显示运行状态
- 成功后展示摘要卡片、分布信息、结果表格
- 失败时展示字段级或表单级错误

选择原因：

- 与当前技术栈最匹配，交付路径最短。
- 结果展示以表格和摘要为主，服务端模板足够胜任。
- 有利于先稳定信息架构，再决定是否升级到更强交互模型。

备选方案：

- 首版直接做前后端分离。未采用，因为当前没有必须依赖复杂客户端状态管理的场景。

### 3. 新增“Web 视图模型”层，隔离 CLI 输出与页面展示

虽然普通回测和策略回测已有 dataclass 结果对象，但页面不应直接依赖 CLI 打印结构。新增一个面向 Web 的序列化/映射层，负责：

- 将 `Decimal`、`date` 等类型转换为页面和 JSON 易消费的格式
- 将普通回测摘要、收益分布、逐笔明细整理成页面块
- 将策略回测摘要、交易记录、未平仓信息整理成页面块
- 标准化错误响应格式，便于表单提示

选择原因：

- 避免页面模板直接耦合领域对象细节。
- 为后续导出 CSV、增加分页或切换 JSON API 留出扩展点。
- 不影响现有 CLI 文本输出逻辑。

备选方案：

- 直接在页面模板中消费领域 dataclass。未采用，因为会导致模板承担过多格式化逻辑。

### 4. 普通回测与策略回测共用表单组件模式，但保持独立路由和结果布局

两类页面都会复用：

- 回测时间区间输入
- 规则输入方式
- 排序与 Top N 参数
- 公共错误提示与结果容器

但仍保持两套独立页面和提交入口：

- 普通回测页强调命中数、胜率、收益分布、逐笔回测明细
- 策略回测页强调账户资产、收益率、已平仓交易、期末持仓

选择原因：

- 两类回测的心智模型不同，合并成一个大表单会增加理解成本。
- 独立页面更符合用户已形成的 CLI 功能认知。

备选方案：

- 一个页面内通过模式切换展示两类回测。未采用，因为字段差异较大，会让表单过于复杂。

### 5. 首版同步执行回测，请求内直接返回结果

普通回测和策略回测首版沿用当前同步计算方式，页面提交后由服务端直接执行并返回结果页面，不引入后台任务表或异步轮询。

选择原因：

- 当前项目还没有任务系统，新增异步作业会显著扩大范围。
- 用户当前痛点是“结果不好看、不易查看”，不是“必须后台排队运行”。

备选方案：

- 后台任务 + 轮询查询。未采用，因为需要任务状态存储、超时恢复和更多运维设计。

## Risks / Trade-offs

- [回测运行时间较长时页面等待明显] → 首版先提供清晰的运行中状态，并保留后续升级为异步任务的接口边界。
- [新增 Web 依赖会扩大运行环境] → 选择轻量、社区成熟的 Python Web 方案，并在文档中补充启动方式。
- [普通回测与策略回测结果量很大，页面首屏过重] → 首版先控制默认展示结构，必要时对明细区做折叠、限定默认行数或增加前端筛选。
- [规则输入仍以 JSON 为主，表单易出错] → 明确提供示例、字段说明和格式化错误反馈，减少用户回到控制台排查的次数。
- [页面层可能与 CLI 口径逐渐漂移] → 强制页面调用现有领域服务，不单独复制回测计算逻辑。

## Migration Plan

1. 新增 Web 入口模块、模板目录和静态资源目录。
2. 补充依赖与启动命令，使本地可以独立启动 Web 页面。
3. 将现有普通回测和策略回测逻辑封装为可供页面直接调用的服务。
4. 实现两个页面、对应提交接口和结果展示组件。
5. 增加基础测试，覆盖参数校验、成功渲染和错误反馈。
6. 在 README 中补充页面入口、启动方式和使用示例。

回滚策略：

- 如页面层出现问题，可直接停用 Web 入口，不影响现有 CLI 回测能力。

## Open Questions

- Web 层是否采用 `FastAPI + Jinja2` 还是 `Flask + Jinja2`，需要在实施时结合团队偏好和依赖体量做最终确认。
- 普通回测收益分布首版是否只做文本统计，还是直接做内嵌图表，需要结合实现复杂度决定。
- 明细结果是否需要首版就支持 CSV 导出，当前提案默认不纳入必需范围。
