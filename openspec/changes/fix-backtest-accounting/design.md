## Context

当前策略回测在循环中分别维护现金、未结算现金、持仓市值和交易明细，期末又重新估值一次，导致摘要与权益曲线可能使用不同的期末状态。实验报告同时保存请求对象和派生摘要，但字段默认值、规则数量及实际执行配置未必来自同一规范化对象。交易金额目前按成交价计算，未包含成本，短周期策略的净收益因此偏乐观。

本变更需要兼容已有 `run_*` 报告，保持 DuckDB/CSV/JSON 存储方式和现有 Python API 的基本调用方式，不引入外部依赖。

## Goals / Non-Goals

**Goals:**

- 建立单一的账户状态结算路径，保证期末资产、现金、持仓市值和盈亏可由同一状态重算。
- 使用规范化后的最终请求配置执行回测并持久化，确保请求、摘要和报告元数据一致。
- 提供可配置且可审计的买入/卖出成本计算，将成本反映到现金、交易盈亏和收益指标。
- 对历史无成本报告保持读取兼容，并能明确标识其成本口径。

**Non-Goals:**

- 本变更不重新设计选股信号、复权算法或市场过滤策略。
- 不在本阶段实现逐笔撮合、盘口冲击或税费地区差异模型。
- 不自动重写历史报告的收益数值；历史报告只做兼容读取和口径标识。

## Decisions

1. **统一账户结算模型**

   在回测循环和最终报告生成前使用同一个 `AccountState` 语义：现金余额、未结算现金、开放头寸及其期末估值均从该状态派生。期末先按最后可用收盘价估值，再生成摘要和最后一条权益曲线，禁止分别维护两套期末市值变量。若价格缺失，采用明确的缺失状态并在报告中标记，不静默混用买入成本和市场价。

   备选方案是只修正摘要公式，但会继续保留权益曲线与摘要分叉，因此不采用。

2. **请求先规范化，再执行和持久化**

   在进入回测前生成不可变的规范化配置对象：规则、日期、排序、仓位、成本参数和功能开关均经过默认值填充与类型转换。执行器、摘要构造器和实验存储器只接收该对象；JSON 序列化使用显式 schema，反序列化支持旧字段和缺省成本配置。规则数量从规范化规则集合计算，不能从另一套默认配置推导。

   备选方案是分别修补 JSON 写入字段，短期改动小但容易再次出现请求/摘要漂移，因此不采用。

3. **成本模型按成交事件计算**

   新增交易成本配置，至少包含佣金比例、印花税比例、过户费比例和买卖滑点；买入和卖出分别计算，印花税默认仅卖出收取。成交价先应用滑点，再计算费用，费用明细写入交易记录，净买入支出从现金扣除，净卖出收入计入未结算现金。默认值保持向后兼容但报告明确 `costs_included`。

   备选方案是交易结束后统一按收益比例扣除估算成本，无法正确处理不同成交金额和买卖方向，因此不采用。

4. **报告与指标以净值序列为准**

   总收益、年化收益、最大回撤、波动率和年度指标统一读取包含成本的权益曲线；交易明细中的毛收益和净收益分开保存。最后一个交易日必须有权益点，即使没有买入或卖出。

## Risks / Trade-offs

- [历史报告缺少成本字段] → 读取时填充零成本并标记 `costs_included=false`，不回写旧数值。
- [缺失收盘价导致期末估值变化] → 明确记录估值来源和缺失原因，并增加测试覆盖。
- [滑点/费率默认值改变既有结果] → 默认配置提供兼容模式，只有显式启用净成本模型时才改变历史策略结果。
- [配置 schema 变更影响网页和 CLI] → 保留旧字段别名和 JSON 宽松读取，新增字段使用稳定默认值。

## Migration Plan

1. 先新增配置、成本计算和报告字段，补充单元测试，不改变旧报告文件。
2. 改造回测执行器和指标计算，生成新版本报告并标记 schema 版本。
3. 对 `run_id=416` 及代表性历史回测重新运行，核对摘要、权益曲线和交易明细可加总。
4. 若发现兼容问题，可回滚执行器代码；旧报告仍可由兼容读取器访问。

## Open Questions

- 默认佣金、印花税、过户费和滑点具体采用哪组市场费率？
- 触及涨跌停、无法按滑点成交时，成本模型是否应跳过成交还是按收盘价成交？
- 期末缺失收盘价时，是否允许使用最后有效收盘价，还是必须将头寸标记为不可估值？
